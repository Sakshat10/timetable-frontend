## 0. Executive summary

1. **The contract is in good shape: there are 99 operations, all under `/api`, all documented in OpenAPI 3.0.3.**
   - Request and response schemas are complete for every module except **substitution** and **curriculum**, which declare no response schema.
   - The authoritative validation is Zod in the controllers.
2. **The schedule model changed since the previous frontend was built.**
   - The schedule is now *working days + periods per day + one `breakAfterPeriod`*, with no clock times (migration `20261117090000`).
   - The old periods/timing-events payloads are refused with 400.
   - Any knowledge carried over from the old frontend about period times, lunch or assembly events is obsolete.
3. **Session-cookie auth is the only option.**
   - The cookie is `session_token`. In production it is `HttpOnly; Secure; SameSite=Strict`, with an absolute lifetime of 7 days.
   - Because of `SameSite=Strict`, **the browser must reach the API on the frontend's own site**.
   - Recommendation: a **same-origin reverse proxy via Next.js `rewrites`** (`/api/*` → backend), plus server-side `fetch` with the forwarded cookie for Server Components. CORS then becomes irrelevant to the browser.
4. **The frontend must normalise four error dialects:**
   - Zod: `errors{field:[msg]}`.
   - Fastify/Ajv: `{message}` only, with no `success` key, returned *before* auth runs.
   - Versions and generation: `data.code`.
   - Substitution: `errors.code[0]`.
5. **Things that do not exist and must not be faked:**
   - generation cancel or progress percentage;
   - unpublish, archive or restore;
   - changing a lesson's teacher, adding or removing a lesson, or moving a lesson across sections;
   - batch moves;
   - any export endpoint;
   - a school-wide workload API;
   - an activity or audit log (only cover events exist);
   - a school time zone ("today" is UTC);
   - password reset;
   - looking up a school by its code (login needs the school's UUID).
6. **Hard product rules the UI must encode:**
   - Structure, curriculum, eligibility, assignments, schedule and generation writes require a **DRAFT** academic year.
   - DRAFT → ACTIVE → COMPLETED is one-way.
   - Editing a version needs a DRAFT version in a DRAFT or ACTIVE year.
   - Substitutions work only from the **PUBLISHED** version of a DRAFT or ACTIVE year whose dates contain the day in question.

**What the year status allows** (combining every module):

| Year status | Allowed |
|---|---|
| DRAFT | Everything: structure, curriculum, eligibility, assignments, schedule, generation, editing, publishing, substitutions. |
| ACTIVE | Edit, lock, publish and clone versions. Substitutions. Reads. **No** structure, curriculum, eligibility, assignment, schedule or generation writes, and the year cannot go back to DRAFT. |
| COMPLETED | Reads only, plus name/date edits. Versions are frozen (`ACADEMIC_YEAR_NOT_EDITABLE`). There are no substitutions for its dates. |

**Product consequence:** once a school activates a year, it can never regenerate that year's timetable. It can still hand-edit drafts with moves and swaps, clone, and publish. The UI must warn before activation.

### 2.2 Can Next.js call the backend directly?

**From the browser, cross-origin: no for production; only "works" in development.**
- In production the cookie is `SameSite=Strict`. A frontend on another *site* (for example `app.vercel.app` → `api.onrender.com`) would never get the cookie sent with `fetch`.
- Same-site subdomains (`app.school.com` → `api.school.com`) would work with `credentials:'include'`. Even then, `Location` and `Retry-After` stay unreadable, and `FRONTEND_URL` allows only one origin, so preview deployments break.

**Recommended: a same-origin BFF proxy with no auth logic of its own.**

```
Browser ──(same origin, cookie is first-party)──> Next.js  /api/:path*
                                                    │ rewrites() to BACKEND_URL/api/:path*  (Set-Cookie passes through)
Server Components / Route Handlers ──fetch(BACKEND_URL, { headers: { cookie: `session_token=${cookies().get(...)}` } })
```

1. Add `next.config.ts` `rewrites()`: `{ source: '/api/:path*', destination: `${BACKEND_URL}/api/:path*` }`.
   - The browser only ever talks to the Next.js origin. The cookie is set on the frontend host, and `Strict` is satisfied.
   - CORS is not involved, all headers are readable, and preview URLs work.
   - The Next.js 16 docs confirm external rewrites (`docs/01-app/03-api-reference/05-config/01-next-config-js/rewrites.mdx`, via Context7).
2. Server-side reads (RSC, route handlers): call `BACKEND_URL` directly and forward **only** `session_token` from `cookies()`. CORS does not apply server-to-server.
3. `proxy.ts` (formerly `middleware.ts` in Next 16) does an **optimistic** check only: is a `session_token` cookie present? If not, redirect to `/login`. The authoritative check is `GET /admin/me` in the protected layout. On 401, redirect to `/login?next=…`. The Next.js auth guide recommends exactly this (no database or API call in Proxy).
4. Never copy the token into JS-readable storage, never expose it to client components, and never use `localStorage`.
5. **Rate limiter and client IP (must decide before production).**
   - Through any proxy, the backend sees the proxy's IP. All users would then share the 5-per-15-minute login allowance.
   - Fix: set the backend's **`TRUST_PROXY`** env (a hop count or the proxy's addresses). This is deployment configuration, not a code change.
   - Also confirm that the Next.js rewrite forwards `X-Forwarded-For`. The docs I fetched do not state this: **verify in Phase 1** with an `app.inject`-free real-server test.
   - Server-side fetches are not rate-limited (only login, register and school creation are), so they are unaffected.
6. **CSRF.** The cookie is `SameSite=Strict` in production and `Lax` in development, and every write needs a JSON body or a non-simple method. Do not add GET routes that write. Note that the backend's cover GETs *do* write internally (`syncSchool`), but those writes are idempotent reconciliation.

**Environment:**
- Frontend: `BACKEND_URL` (server-only), e.g. `http://127.0.0.1:4000`, or `4010` for the disposable e2e backend.
- Backend: keep `FRONTEND_URL` set to the frontend origin. With the proxy it barely matters, but it must stay valid.

### 2.3 Session UX contract

- **App boot:** `GET /admin/me` (server-side in the root protected layout), then `GET /schools/:schoolId` for the name.
- **Any 401 on a client fetch:** clear the query cache, then redirect to `/login?next=<path>` with a single "Your session ended" notice. Deduplicate it so parallel requests show one notice.
- **429 on login:** show "Too many attempts, try again in up to 15 minutes". The server sends no `Retry-After`.
- **Expiry:** an absolute 7 days. The UI cannot extend a session.
- **Login form:** needs the school id. Options for UX: remember the last school id on the device (it is not a secret), or accept the "school code" and keep a local mapping. **There is no backend lookup** (see §9).

### 3.1 Eligibility versus specific assignment (the important distinction)

| Concept | Model | Meaning | Required? | Used by |
|---|---|---|---|---|
| **Subject qualification** | `TeacherSubject` | "This teacher can teach Maths." School-wide, no year. | Always required for any teaching assignment, whether explicit or automatic. | feasibility, generation, assignment validation, substitute ranking (as a soft signal only) |
| **Grade eligibility** | `TeacherSubjectGrade` rows, **or** `TeacherSubject.gradeScope = ALL_GRADES` | "…for Grades 6-8 of *this* year." It is year-scoped through the grade. | Required. Nothing is permitted by omission. | same |
| **Specific assignment** | `SectionSubjectTeacher` | "Rahul teaches Maths to **6A**." A hard pin. | **Optional.** Without it, generation **auto-allocates** an eligible teacher using the same allocator as feasibility (`TEACHER_AUTO_ASSIGNED` warning). The automatic choice is **never stored** as an assignment. | feasibility capacity, the generation input (fixed teacher) |

Consequences for the UI:
- Eligibility *defines the candidate pool*. Assignments *override* the allocator for one section.
- An assignment must stay valid: an active teacher, the subject link, and grade eligibility. Otherwise readiness reports a blocker; it is never silently replaced.
- Deactivating a teacher *keeps* their assignments, which then become `INACTIVE_ASSIGNED_TEACHER` errors.
- The teacher actually chosen for each lesson is visible only in the generated timetable entries. The UI must not present "who teaches 6A Maths" as configured when it was auto-allocated.

### 3.2 Timetable version data

- Entries reference live sections, subjects and teachers, so the view shows **current** names.
- A version also freezes `inputSnapshot`: the grid and the normalised problem.
  - Moves are validated against the **snapshot**.
  - Publishing is validated against the **live** configuration, which is where staleness comes in.

## 4. Generation workflow specification

### 4.1 Sequence

```
1. GET /timetable-feasibility?academicYearId=Y          (show blockers/warnings; gate the button)
   gate = year.status === 'DRAFT' && report.status === 'READY'
2. POST /timetable-generations { academicYearId: Y, options? }   → 202 { generationRunId, timeLimitSeconds, … }
   Put the run id in the URL immediately (?run=<id>).
3. Poll GET /timetable-generations/:id  every 2-3 s while status ∈ {QUEUED, RUNNING}
   (refetchInterval; stop on SUCCEEDED/FAILED; pause when tab hidden, resume on focus)
4a. SUCCEEDED → run.versionId (may be null later if the draft is deleted; run.versionDeleted)
    → navigate to /…/versions/<versionId>; invalidate the versions list
4b. FAILED → run.failure{ code, message, diagnostics } → map code to guidance (table 4.3); the only retry is a new POST
```

### 4.2 Run object (`timetable-generation.schema.ts:47-147`)

**Fields:**
- `id, academicYearId`, `status: QUEUED|RUNNING|SUCCEEDED|FAILED`, `phase: string|null`
- `attempts, seed, reproducible, timeLimitSeconds, workers, sectionCount`
- `createdAt, startedAt, completedAt, updatedAt`
- `versionId|null, versionDeleted, sourceVersionId|null, lockedEntryCount`
- `result|null`: solverStatus, solutionSource, fallbackReason, runtimeSeconds, weightedObjective, warnings[], versionId, versionNumber, entryCount, …
- `failure: {code, message, diagnostics}|null`

**Phases, in order:**
1. `null` (queued)
2. `CLAIMED`
3. `SNAPSHOT`
4. `FEASIBILITY`
5. `NORMALIZE`
6. `BASELINE`
7. `SOLVING`
8. `VALIDATING`
9. `METRICS`
10. `PERSISTING`
11. `DONE`

On failure, `phase` stays at the step that failed. **There is no percentage.** Show the phase as a stepper, plus elapsed time against `timeLimitSeconds`.

**Expected duration by section count:**

| Sections | Time budget |
|---|---|
| ≤10 | 10 s |
| 11–50 | 60 s |
| 51–100 | 120 s |
| >100 | 180 s |

- The cap is 300 s, and the watchdog allows +20 s.
- A `reproducible` run uses about 45% of the budget.
- Queue wait comes on top of this.
- Caveat: `timeLimitSeconds` on the run is computed from all sections. `result.timeLimitSeconds` is the value actually used.
- Refs: `timetable-generation.time-policy.ts:24-31,84-107`, `orchestrator.ts:215`.

### 4.3 Failure codes and suggested UI handling (`timetable-generation.contracts.ts:42-64`)

| Code | Meaning | Suggested UI action |
|---|---|---|
| NOT_READY / YEAR_NOT_DRAFT | The configuration changed after enqueue | Re-run readiness |
| CONFIGURATION_CHANGED | Edited during the run; nothing was written | Regenerate |
| INFEASIBLE_HARD_CONSTRAINTS / NO_SOLUTION_WITH_LOCKS / LOCKS_INVALID | No timetable exists under these constraints or locks | Unlock or adjust, then regenerate |
| DRAFT_LIMIT_REACHED | The draft cap was hit at persist time | Delete or publish drafts |
| QUEUE_EXPIRED | Queued for more than 30 min without running (for example, the runner is disabled) | Retry; mention server capacity |
| WORKER_LOST / PERSIST_FAILED / SOLVER_UNAVAILABLE / SOLVER_CRASHED / SOLVER_INVALID_OUTPUT / SOLVER_MODEL_INVALID / SOLVER_INPUT_REJECTED / INTERNAL_INCONSISTENCY | Server-side faults | Generic retry; show the code for support |

### 4.4 Recovery and idempotency rules

- **POST is not idempotent.** If the answer is lost (network error, 5xx or timeout), **never re-POST blindly**. Run `GET /timetable-generations?academicYearId=Y&limit=5` and adopt the newest QUEUED or RUNNING run, or a SUCCEEDED/FAILED run created after the click time. A blind re-POST after the first run finished creates a second draft.
- **409 "already queued or running":** adopt `data.existingRunId`. If it is null, the run just finished: read the list.
- **Page reload:** take the run from the URL. Otherwise read the list and resume polling any QUEUED or RUNNING run for the year.
- **Server restart:** the run is requeued automatically; a graceful restart consumes no attempt. A hard crash is retried once after the 90 s lease, then fails with `WORKER_LOST`. Polling simply continues.
- **503:** back off by `Retry-After` (readable only through the same-origin proxy). Otherwise wait 30 s for "queue full" and 2 s for `BUSY`.
- **Concurrency:** one active run per year (DB-enforced). The draft cap counts DRAFT versions, default 20.

### 4.5 Draft creation

- Success always creates a **new DRAFT** version: `versionNumber = max+1` (numbers of deleted versions can be reused), `revision 1`.
- `solutionSource` is CP_SAT, or BASELINE when the solver timed out cleanly.
- `metrics.terms`: teacherRun3, teacherRun4Plus, subjectSameDayExcess, sectionHoles, dailyLoadExcess.
- Nothing is published automatically.
- **Regenerate keeping locks:** `options.sourceVersionId = <draft>`. Its locked lessons are frozen at POST time.

## 5. Advanced editor workflow specification

### 5.1 Loading a draft

**Requests:**
1. `GET /timetable-versions/:id`: status, revision, all `entries[]` (ids only), lockedCount, manualEditCount.
2. `GET /timetable-versions/:id/timetable?view=section&id=<sectionId>`, once per section shown. The response contains:
   - `version{id,…,revision}` and `subject{type:'SECTION',…}`
   - `grid{ days[{dayOfWeek,index}], periods[{periodNumber, continuesIntoNext, startTime|null,…}] }`
   - `cells[{dayOfWeek, periodNumber, lesson|null}]`, where a lesson is `{ entryId, section, subject, teacher{id,name,isActive}, subjectRequirementId, isLocked, source }`
   - `totals{…}` and `periodTimes{source:'NONE'|'SNAPSHOT'|'CURRENT'|'UNAVAILABLE',…}`
3. `GET /timetable-versions/:id/validation` for the publish gate.

**Rendering rules:**
- **The break** sits after the period whose `continuesIntoNext === false` and that is not the last period. The view has no `breakAfterPeriod` field.
- **Whole-school editor:** there is no whole-version grid endpoint. Build the model from `GET :id` (entries) joined with sections, subjects and teachers (setup reads), and use the snapshot grid from any one view call.
- **Teacher view:** use the same endpoint with `view=teacher`.

### 5.2 Move and swap: `POST /timetable-versions/:id/moves`

**Body (strict):**
```json
{ "entryId": "uuid", "to": { "dayOfWeek": "MONDAY", "periodNumber": 3 }, "swapWithEntryId": "uuid?", "expectedRevision": 7 }
```
Unknown keys, such as `teacherId`, are a 400.

**Semantics:**
- **MOVE:** the lesson goes to an empty slot of **its own section**.
- **SWAP:** two lessons of **the same section** exchange slots, and `to` must equal the partner's slot.
- **Not possible:** moving across sections, changing the teacher or subject, adding or removing a lesson, or batch moves. Nothing exists for these (`timetable-version.edit-core.ts:14-16,277`).

**Success (200):**
- `data{ versionId, mode: MOVE|SWAP, revision (= expected+1), changedEntries[], metrics, metricsDelta, manualEditCount, lockedCount }`.
- The moved entries become `source:'MANUAL'`. They are not locked.

**Refusals** (`data.code`; checked in this order):

| Code | Status | Meaning | Details |
|---|---|---|---|
| ENTRY_NOT_FOUND | 404 | none | none |
| VERSION_NOT_DRAFT | 409 | none | `{status, revision}` |
| ACADEMIC_YEAR_NOT_EDITABLE | 409 | The year is COMPLETED | `{yearStatus}` |
| REVISION_CONFLICT | 409 | Someone else edited the version | `{revision, status}` |
| SNAPSHOT_UNUSABLE | 409 | none | none |
| INVALID_SLOT | 400 | Not a working day or period of the snapshot grid | none |
| INVALID_SWAP / INVALID_MOVE | 400 | none | none |
| ENTRY_LOCKED | 409 | none | `{entryId}` |
| SLOT_OCCUPIED | 409 | none | `{occupantEntryId}`: offer "swap instead" |
| TEACHER_BUSY | 409 | none | `{entryId}`: the conflicting entry is **not** identified |
| INVARIANT_VIOLATION | 409 | none | `{violations: first 5}` |
| BUSY | 503 | none | `Retry-After: 2` |

**Hard constraints re-validated on every move:**
- section and teacher collisions;
- period counts per requirement;
- teacher capacity (32 per week, or the number of weekly slots);
- day and period validity.

**Not checked by moves:**
- absences;
- unavailability;
- the break (it only affects metrics).

Ref: `timetable-version.edit-service.ts:100-161`, `timetable-version.edit-core.ts:253-317`.

### 5.3 Locks: `PUT /timetable-versions/:id/locks`

- **Body:** `{ entryIds: uuid[1..1000] (unique), locked: boolean, expectedRevision }`.
- **Behaviour:** all-or-nothing; an unknown id is `404 ENTRY_NOT_FOUND`. The revision goes up by 1 only when something changed.
- **Response:** `{ versionId, locked, changed, unchanged, revision, lockedCount }`. **Which ids changed is not returned.**
- **What locks do:**
  - block moves (`ENTRY_LOCKED`);
  - are frozen into a regeneration started with `sourceVersionId`.
- **Stale route text:** the description at R:457 says "not used by generation yet". The code shows they are.

### 5.4 Validation: `GET /timetable-versions/:id/validation`

Read-only; works for any status.

**`data` fields:**
- `versionId, status, revision`
- `valid`, `violations[≤50]{code,message,sectionId?,teacherId?,dayOfWeek?,periodNumber?,assignmentId?}`, `violationCount`
- `isStale`, `metrics|null`
- `informational{ staleReason, configurationIssues[≤20], academicYearStatus, entryCount, lockedCount, manualEditCount, publishable, stats }`

**Errors:** `409 SNAPSHOT_UNUSABLE`.

**`publishable`** = `status==='DRAFT' && year is DRAFT or ACTIVE && valid && !isStale`. It is **advisory**: it ignores `expectedPublishedVersionId`. Compare `validation.revision` with the editor's revision before trusting it.

### 5.5 Publishing: `POST /timetable-versions/:id/publish`

- **Body (strict, both fields required):** `{ expectedRevision, expectedPublishedVersionId: uuid|null }`, where `null` asserts that no version is currently published. Read the current published id from the versions list.
- **What it does, in one transaction:**
  1. Re-validates against the **live** configuration.
  2. Archives the previous published version.
  3. Publishes this one.
  4. After commit, reconciles substitutions and auto-allocates covers. That result is reported as `data.substitution: {status:'COMPLETED', run{considered,assigned,unfilled,conflicts,skippedPast,heldForReview}} | {status:'FAILED', error}`.
- **200 response:** `{ versionId, status:'PUBLISHED', revision, publishedAt, archivedVersionId|null, substitution }`.
- **Refusals:**

| Code | Details / notes |
|---|---|
| VERSION_NOT_DRAFT | After a lost response this **means it already succeeded**: re-read. |
| ACADEMIC_YEAR_NOT_EDITABLE | none |
| REVISION_CONFLICT | none |
| PUBLISHED_CHANGED | `{publishedVersionId}` |
| SNAPSHOT_UNUSABLE | none |
| STALE_CONFIGURATION | `{reason: CONFIGURATION_CHANGED\|CONFIGURATION_NOT_NORMALIZABLE, issues?}` |
| VALIDATION_FAILED | `{violationCount, violations≤20}` |
| BUSY (503) | none |

- **Not available:** unpublish, archive, restore. To roll back, **clone the archived version and publish the clone**. A clone is as stale as its source, so this only works if the configuration has not changed since.

### 5.6 Clone: `POST /timetable-versions/:id/clone`

- **Body:** an optional strict `{ lockMode?: KEEP|ALL|NONE (default KEEP), includeStaleness?: boolean }`.
- **Rules:**
  - Any source status can be cloned.
  - The year must be DRAFT or ACTIVE.
  - Cap: drafts + active runs < `MAX_DRAFTS_PER_YEAR`, otherwise 409 `DRAFT_LIMIT_REACHED {drafts, maxDraftsPerYear, pendingRun}`.
- **Result:** a new DRAFT of the **same year** with `revision 1`. It copies the snapshot, hash and metrics, so it is exactly as stale as the source.
- **Response:** 201 with `clonedFromId, clonedFromVersionNumber, lockMode, periodTimesCaptured`, plus a `Location` header.
- **Not idempotent.** After a lost response, diff the versions list. The list does not show `clonedFromId`, so new drafts are only "probably" the copy.

### 5.7 Delete: `DELETE /timetable-versions/:id`

- **DRAFT:** send **no body**. A body of `{}` is a 400. Also do not send `Content-Type: application/json` without a body.
- **PUBLISHED or ARCHIVED:** body `{ confirmVersionNumber, expectedStatus, expectedRevision }` is required.
  - Without it: `409 CONFIRMATION_REQUIRED {status, versionNumber}`.
  - Other refusals: `400 CONFIRMATION_MISMATCH`, `409 STATUS_CHANGED`, `409 REVISION_CONFLICT`, `409 ACADEMIC_YEAR_NOT_EDITABLE`, `409 VERSION_HAS_HISTORY {coverRequests, coverRequestTotal}` (any cover request blocks), `503 BUSY`.
- **200 response:** `{ versionId, versionNumber, status, lessonsRemoved, publishedVersionNow: null, detachedClones }`. Deleting the published version leaves **no** published timetable; nothing is promoted in its place.

### 5.8 Revision concurrency, undo/redo and saving

**Revisions:**
- `revision` goes up by 1 on each move or swap, on each lock call that changes something, and on publish (for both the target and the archived version).
- `expectedRevision` is required by moves, locks, publish and the confirmed delete. Clone and draft delete do not need it.
- **On REVISION_CONFLICT:** refetch `GET :id` and the visible views, and tell the user. Never auto-retry a different user's intent.

**Saving:**
- **Each operation is its own committed save.** There is no "draft of a draft" and no Save button.
- The UI should present every change as applied immediately, and show "Unpublished changes" against the published version.

**Undo/redo (client-side only; no server support):**
- Undo of a MOVE is a move back to the old slot. Undo of a SWAP is the same swap again. Undo of a lock is the opposite lock on the ids the client recorded.
- Each undo is a **new revision** and can be refused (REVISION_CONFLICT, ENTRY_LOCKED, SLOT_OCCUPIED, TEACHER_BUSY).
- Moved lessons stay `MANUAL` forever, even when moved back.
- Keep the stack per version and clear it on any conflict or external change.

**Optimistic UI:**
- Pessimistic updates are safer: server validation is complex (counts, capacity, collisions).
- Apply `changedEntries` from the response directly. It is authoritative and avoids a full refetch.
- Show a pending state on the dragged cell.

**Client-side hints before a request:**
- These are only for UX. The server stays authoritative.
- Mark target cells: occupied (offer swap), locked, or teacher busy (computed from the loaded entries).

**Conflict detection across users:**
- There is no push. Poll `GET :id` (cheap revision check) every ~20 s while the editor is focused, or on window focus.

## 6. Substitution workflow specification

### 6.1 Daily operations flow

```
Record absence  POST /teacher-absences { teacherId, startDate, endDate, scope, from/toPeriod, reason, autoAssign:true }
   → server materialises CoverRequests from the PUBLISHED version of the DRAFT/ACTIVE year containing each date
     (no published version → datesWithoutPublishedTimetable; two years overlap → ambiguousDates)
   → automatic allocation runs (status COMPLETED|FAILED|DISABLED; FAILED still returns 201 → offer retry)
Review         GET /teacher-absences/:id/substitution-summary   (assigned / unfilled / attention per lesson)
               GET /substitutions?from=D&to=D[&status=OPEN,ASSIGNED]  (daily board; total + paging)
Manual cover   GET /substitutions/:id/candidates → PUT /substitutions/:id/assignment { teacherId[, confirmFourConsecutive] }
Unassign       DELETE /substitutions/:id/assignment   (→ OPEN)
Cancel lesson  POST /substitutions/:id/cancel { reason }   (lesson not happening / covered otherwise)
Retry          POST /teacher-absences/:id/auto-assign  or  POST /substitutions/auto-assign { from, to }
Edit absence   PATCH /teacher-absences/:id     Cancel absence  POST /teacher-absences/:id/cancel
Unavailability POST /teacher-unavailability { teacherId, date, periodNumber? }  /  DELETE …/:id
History        GET /substitutions/:id (history[]),  GET /substitution-events (feed)
```

"Finding affected lessons" before saving is **not** a separate API. Choose one:
- create the absence and read the result (`coverRequestsCreated`, then the summary); or
- preview client-side from the published version's teacher view: `GET /timetable-versions/<publishedId>/timetable?view=teacher&id=` on that weekday.

### 6.2 Rules the UI must respect

**Dates and time:**
- All dates are `YYYY-MM-DD` **UTC calendar dates**.
- "Today" is the UTC date: for an IST school, 00:00–05:29 local time is still "yesterday". Weekdays are the UTC weekday of the date.
- Format labels from the date components and never through the browser time zone.
- Past dates are never auto-assigned (`skippedPast`), but they can be assigned manually.

**Overlaps:**
- Absence overlap means both the dates and the periods overlap: `409 ABSENCE_OVERLAP` with `errors.absenceId`.
- `TEACHER_IS_COVERING` (409) is raised when the absent teacher was *manually* assigned to cover inside the range. Automatic covers are released and reallocated instead.

**Edits and cancellations:**
- PATCH cannot change the teacher. FULL_DAY ⇄ PERIODS changes follow the shape rules.
- Lessons that fall outside the new range are cancelled, except **manual** assignments, which return `409 ASSIGNED_COVERS_OUTSIDE`.
- Cancelling an absence is blocked only by **manual** assignments (`409 ASSIGNED_COVERS_EXIST`). Automatic assignments and OPEN requests are cancelled with it.

**Cover request statuses:**
- OPEN → ASSIGNED (MANUAL or AUTOMATIC) → OPEN (unassign or auto-release) → CANCELLED or OBSOLETE (both final).
- **OBSOLETE** is set when a new version is published, for future dates. The successor request has `supersedesId`. A successor of a manually assigned request is held with the attention code `MANUAL_ASSIGNMENT_NEEDS_REVIEW`.

**What auto-allocation touches:**
- Only OPEN requests. It never overwrites an ASSIGNED one.
- Re-calling it is idempotent and **is** the retry mechanism.

**Attention codes:**
- NO_AVAILABLE_TEACHER, NO_QUALIFIED_TEACHER, CONSECUTIVE_PERIODS_NOT_ALLOWED, MANUAL_ASSIGNMENT_NEEDS_REVIEW.
- PAST_DATE appears only in the summary.
- The README's `ONLY_LAST_RESORT_CANDIDATES` does not exist in code.

**GETs that write:**
- `GET /substitutions*` runs `syncSchool`, which writes. It is still safe to call on render, but do not poll it aggressively.

### 6.3 Candidates and manual cover

**Hard exclusions**, in order:
1. IS_ABSENT_TEACHER
2. INACTIVE
3. ABSENT
4. UNAVAILABLE
5. TEACHING_ANOTHER_LESSON
6. ALREADY_COVERING
7. CONSECUTIVE_NOT_ALLOWED (NEVER_ALLOW only)

**No subject link or grade eligibility is required.**

**Tiers:**

| Tier | Key | Condition |
|---|---|---|
| 1 | `SAME_SUBJECT` | the teacher has a subject basis (PRIMARY link > SECONDARY link > teaches it in the timetable) |
| 2 | `OTHER_AVAILABLE` | no subject basis; `temporaryUnqualified:true` |
| 3 | `LAST_RESORT` | the assignment would create a run of ≥4 consecutive periods |

- The route text says `OTHER_ELIGIBLE`. **The code uses `OTHER_AVAILABLE`.**
- Under `PREFER_AVOID` (the default), tier 3 is returned with `offered:false` while tiers 1 or 2 exist.
- Assigning a tier 3 needs `confirmFourConsecutive:true`, otherwise `409 FOUR_CONSECUTIVE_CONFIRMATION_REQUIRED` (`errors.periods`).
- Under `NEVER_ALLOW` the answer is always `409 FOUR_CONSECUTIVE_NOT_ALLOWED`.

**Candidate fields:**
- `id, name, employeeCode, tier, tierKey, offered, recommended, requiresConfirmation, subjectBasis, sameSubject, gradeEligible`
- `weeklyLoad, recentCovers (28 days), coverLoadToday, temporaryUnqualified`
- `consecutive{resultingRun,from,to,periods[],createsFourConsecutive,threshold:4}`
- `explanation`

**Envelope:** `selection{summary, counts, recommendedTeacherId,…}`, `policy`, `excludedCounts`, `message?`, `excluded?[]`.

**Assignment errors** (`errors.code[0]`):

| Code | Status |
|---|---|
| COVER_OBSOLETE, COVER_CANCELLED | 409 |
| IS_ABSENT_TEACHER, INACTIVE | 400 |
| ABSENT, UNAVAILABLE, TEACHING_ANOTHER_LESSON, ALREADY_COVERING | 409 |
| FOUR_CONSECUTIVE_* | 409 |
| REPLACEMENT_ALREADY_BOOKED | 409 |
| NOT_ASSIGNED (unassign) | 409 |

**Re-PUT of the same teacher:** pins an AUTOMATIC assignment to MANUAL.

Ref: `substitution.service.ts:501-664`, `substitution.core.ts:88-259`, `substitution.evaluate.ts`.

### 6.4 Teacher workload: what data exists

| Metric | Source | Scope and limitations |
|---|---|---|
| Teaching periods per week | `GET /timetable-versions/:id/timetable?view=teacher&id=T` → `totals.lessons`, `totals.perDay[]`, `totals.bySection[]` | One teacher per call; any version; weekly pattern only (no dates, absences or covers) |
| Free periods | the same call → `totals.freeSlots`; `cells[].lesson === null` per day and period | same |
| Daily workload (pattern) | `totals.perDay[{dayOfWeek, lessons}]` | same |
| Daily workload on a date | **Not available.** Derive: the teacher view for that weekday, minus own-absence slots (`/teacher-absences?teacherId&from&to`), plus that date's ASSIGNED covers (`/substitutions?replacementTeacherId=T&status=ASSIGNED&from=D&to=D`) | Client-side composition |
| Weekly load including covers | Only per candidate (`candidates[].weeklyLoad`, Monday–Sunday) and in `AUTO_ASSIGNED` event `details` | Not available for an arbitrary teacher |
| Cover counts | `GET /substitutions?replacementTeacherId=T&status=ASSIGNED&from&to` → `total`. School-wide: page `status=ASSIGNED` and group by `replacementTeacher.id` | Up to 500 rows per page |
| Planned load against capacity | `GET /timetable-feasibility` → `breakdown.teachers[{assignedPeriods, capacity, remainingCapacity}]` and `limits` | **Explicit assignments only**; auto-allocated demand is not attributed per teacher |
| Thresholds | Constant `maxTeacherPeriodsPerWeek: 32` (effective `min(32, weeklySlots)`); consecutive threshold 4 | **No per-teacher, per-day or configurable limits** |
| School aggregate stats | `GET /timetable-versions/:id/validation` → `informational.stats` (teacherGapPeriods, teacherMaxRun, teacherBusyDays, …) | Totals only, not per teacher |

**A school-wide workload summary API does not exist.** For a workload page, compute it client-side from:
- `GET /timetable-versions/<published>`: all entries with `teacherId, dayOfWeek, periodNumber`. One call gives every teacher's weekly pattern.
- the schedule grid;
- a date-ranged covers query.

### 6.5 Activity feed: `GET /substitution-events`

- **Contents:** a UNION of cover events (excluding CREATED) plus `ABSENCE_RECORDED` and `ABSENCE_CANCELLED`. Ordered oldest first. Each item:
  - `id, type, occurredAt, absenceId, coverRequestId, date, periodNumber`
  - `absentTeacher, fromTeacher, toTeacher, automatic, message, details`
- **Types:**
  - SUBSTITUTE_AUTO_ASSIGNED, NO_SUBSTITUTE_AVAILABLE, SUBSTITUTE_RELEASED
  - ASSIGNMENT_CHANGED, SUBSTITUTE_REPLACED, ASSIGNMENT_CANCELLED
  - COVER_OBSOLETED
  - ABSENCE_RECORDED, ABSENCE_CANCELLED
- **Paging:** `limit` 1..500; the cursor takes precedence over `since`.
- **Using it as a bell:**
  - Bootstrap with `since=<now>`, then follow `nextCursor`.
  - There is no read/unread state, so keep a "last seen" marker per device.
- **Not emitted:** absence edits, unavailability changes, settings changes, setup or publish actions.
- **Polling-gap risk:** `cover_events.createdAt` defaults to `CURRENT_TIMESTAMP`, which is the transaction *start* time (`prisma/migrations/20261023090000_add_substitutions/migration.sql:97`). Allocation transactions can last up to 30 s (`substitution.auto.ts:240`). An event can therefore commit with a timestamp earlier than a cursor a poller has already passed. Mitigation: overlap the poll window (re-read with `since = lastSeen − 60 s` and deduplicate by `id`).

## 8. Recommended Next.js architecture

### 8.1 Structure

```
app/
  (public)/login, signup
  (app)/layout.tsx              ← server: GET /admin/me (cookie forwarded); 401 → redirect('/login?next=')
  (app)/dashboard
  (app)/subjects, teachers, teachers/[id], settings, operations/...
  (app)/y/[yearId]/layout.tsx   ← server: GET /academic-years/:id → YearContext (status → readOnly)
  (app)/y/[yearId]/{classes,curriculum,assignments,schedule,generate,versions,versions/[vid],workload}
proxy.ts                        ← optimistic cookie-presence redirect only
next.config.ts                  ← rewrites /api/:path* → BACKEND_URL/api/:path*
lib/api/
  client.ts      fetch wrapper (base '/api' in browser, BACKEND_URL on server), JSON only, no body → no Content-Type
  server.ts      serverFetch(): forwards session_token from cookies(); 'server-only'
  errors.ts      ApiError + normalise()
  endpoints/     one file per backend module (typed functions; no fetch in components)
  schemas/       zod response schemas for modules without OpenAPI response schemas
  query-keys.ts  key factory
features/<module>/  components, hooks (useQuery/useMutation), rules (pure, unit-tested)
components/ui/      shadcn/ui
```

### 8.2 API client and error normalisation

```ts
type ApiError = {
  status: number;              // 0 = network/timeout
  code: string | null;         // data.code ?? errors.code?.[0] ?? null
  message: string;             // safe message; 500 → generic text, never the raw body
  fieldErrors: Record<string, string[]>; // Zod errors minus 'code'; Ajv → { _form: [message] }
  details: Record<string, unknown>;      // data (minus code) or errors extras (blockedBy, periods, coverRequestIds…)
  retryAfterMs: number | null; // Retry-After header (readable via same-origin proxy)
  uncertain: boolean;          // network error / 5xx / timeout on a WRITE → outcome unknown, never auto-retry
};
```

Rules:
- Writes are never retried automatically, except 503 `BUSY` / queue full, which are retried after `Retry-After` up to N times.
- For an uncertain outcome, re-read state and reconcile.
- Map field paths, such as `grades.0.sections.1.code`, onto form rows.

### 8.3 Types

- **Generate** TypeScript types with `openapi-typescript` from a **checked-in snapshot** of `/docs/json`. Produce the snapshot by running the backend, or with the in-memory dump used in this audit, which needs no database.
- Use the generated types for every module that has response schemas: auth, structure, teachers, requirements, assignments, schedule, feasibility, generation, versions.
- **Hand-write Zod schemas** for **substitution** and **curriculum** (no response schemas). Base them on the services and the live captures in `e2e/dashboard/API_CONTRACTS.md` and `.run/api-contracts.json`. Parse them at runtime in development and test.
- Caveats:
  - Version request schemas in OpenAPI are **documentation only** and differ from Zod. For example, OpenAPI shows a `dayOfWeek` enum, while Zod accepts any string of 1–20 characters. Treat the Zod source as authoritative for request types.
  - Fastify strips undeclared response fields, so OpenAPI response types are reliable. Re-generate whenever the backend changes.
- **Contract tests:** run a small suite against the disposable backend (`e2e/dashboard/e2e.sh`, port 4010). It should assert the shapes the frontend parses, including the four error dialects.

### 8.4 Data fetching, caching and invalidation

- **Library:** TanStack Query for all client data. Server Components prefetch the first screen where it helps (dehydrate/HydrationBoundary). The read pages that benefit are the viewer, versions list and dashboard.
- **Default rendering:** client components for interactive modules (editor, generation, operations, setup forms).
- **Server Components** are safe for:
  - the auth gate;
  - the year layout (status → read-only);
  - static shells;
  - read-only print/export pages.
- **Never cache API reads in the Next.js data cache:** use `cache: 'no-store'`, because responses are per-session.
- Query keys: `['me']`, `['years']`, `['year', id]`, `['grades', yearId]`, `['curriculum', yearId]`, `['teachers']`, `['teacher', id, 'links']`, `['eligibility', linkId]`, `['assignments', yearId]`, `['schedule', yearId]`, `['feasibility', yearId]`, `['runs', yearId]`, `['run', id]`, `['versions', yearId, {staleness}]`, `['version', id]`, `['view', vid, view, entityId]`, `['validation', vid]`, `['covers', filters]`, `['cover', id]`, `['candidates', id]`, `['absences', filters]`, `['absence', id, 'summary']`, `['unavailability', filters]`, `['events']`, `['subSettings']`.
- **Invalidation matrix:**

| After | Invalidate |
|---|---|
| Any setup write | `curriculum`, `feasibility`, `versions` (staleness), plus the entity list |
| Run SUCCEEDED | `runs`, `versions` |
| Move or lock | Apply `changedEntries` to `version` and the affected `view`s; invalidate `validation` |
| Publish | `versions`, `version`, `validation`, `covers`, `events` |
| Clone or delete | `versions` |
| Substitution writes | `covers`, `cover`, `absence summary`, `candidates`, `events` |

- **Staleness:** `includeStaleness=true` costs one normalisation per call. Request it on the versions page and the dashboard, not on every list.

### 8.5 Academic-year context

- Put the year in the URL (`/y/[yearId]/…`) so deep links and the back button work. Remember the last year per device in `localStorage`, as a convenience only.
- **Default year:** the ACTIVE year if there is one, else the newest DRAFT. Remember that "one ACTIVE year" is not enforced (§9).
- Derive `canEditStructure = status === 'DRAFT'` and `canEditVersions = status !== 'COMPLETED'` once, in the year layout. Use them to disable controls with an explanation rather than hiding them.
- Subjects and teachers are school-wide pages. Eligibility rows must be filtered to the selected year client-side.

### 8.6 Pagination and filtering

- Server pagination exists only for covers (limit/offset), events (cursor) and runs (limit).
- Everything else is a full list. Filter and sort client-side with `@tanstack/react-table`, which suits school-sized data (hundreds of rows).

### 8.7 Loading and error boundaries

- **Route-level `loading.tsx`:** skeletons.
- **`error.tsx`:** generic, never shows raw messages.
- **Per-query states:** empty, error with retry, and stale ("showing previous data").
- **Background refetch failures:** if data already exists, keep showing it and add a non-blocking notice. Never replace a working page with an error.
- **401:** handled globally by the client (§2.3).

## 10. Risks and integration constraints

1. **Cookie policy versus topology.** `SameSite=Strict; Secure` in production makes a same-origin proxy mandatory unless the frontend and API share a registrable domain. Decide the deployment topology before Phase 1 ends.
2. **Client IP behind the proxy** (§2.2 item 5). Without `TRUST_PROXY`, one user's failed logins lock out everyone.
3. **Activation is irreversible**, and it ends generation for the year. This is a high-consequence action; it needs typed confirmation.
4. **Staleness everywhere.** Any curriculum, assignment, eligibility or schedule edit makes every draft unpublishable. The UI must show staleness on versions and warn before setup edits when drafts exist.
5. **Draft cap (20) and a global queue (10, shared across schools).** Expect 409 and 503 in normal use; design copy for them.
6. **Non-idempotent writes** (generation, clone, absence create, publish). Every "uncertain" outcome must re-read rather than retry.
7. **UTC dates** in operations (§6.2).
8. **Contract drift.** OpenAPI response schemas strip undeclared fields, so a backend change that forgets the schema silently removes data. Pin the OpenAPI snapshot and run the contract tests in CI against the e2e backend.
9. **Performance.**
   - The views are one entity per call; an "all sections" print means N calls (use bounded concurrency).
   - The versions list with staleness, feasibility and validation all recompute on each call. Do not poll them; refresh on focus or after writes.
10. **Legacy data.** Schedules with `legacy:true` and versions with `periodTimes.source: SNAPSHOT|UNAVAILABLE` still exist. Render them read-only and offer the `breakAfterPeriod` conversion.
11. **Knowledge from the previous frontend is partly obsolete.** For example, it assumed clock-time periods and events, a `/assignments` deep link, and different tier names. Use this document, not the old notes.
12. **Test environment.** The e2e backend's login limiter and the seed's "today" anchor (the next Monday on weekends) cause false failures. Restart and reseed via `e2e.sh`.
